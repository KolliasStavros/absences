# Ενημερώσεις με αλλαγές βάσης

Οι επόμενες ενημερώσεις μπορούν να περιέχουν μαζί κώδικα και SQL μεταβολές. Ο admin ελέγχει την υπογραφή, βλέπει την προεπισκόπηση και επιβεβαιώνει μία φορά με τον προσωπικό κωδικό. Η εφαρμογή κρατά επαληθευμένο backup πριν από οποιαδήποτε αλλαγή και εφαρμόζει τις SQL εντολές πριν από τα νέα αρχεία.

## Μία προετοιμασία στην παλιά εγκατάσταση

Για να υποστηρίζονται μελλοντικοί νέοι πίνακες χωρίς κάθε φορά χειροκίνητη αλλαγή της σταθερής λίστας:

1. Κρατήστε πλήρες backup αρχείων και βάσης από τη συντήρηση ή τον υπεύθυνο hosting. Σε εγκατάσταση με ήδη ενεργή Βαθμολογία που δεν αναγνωρίζεται από τον παλιό μηχανισμό, το backup γίνεται πρώτα από το hosting.
2. Σε ήσυχο χρόνο χωρίς ενεργές καταχωρίσεις, αντιγράψτε από το νέο πακέτο προετοιμασίας τα `includes/lifecycle.php`, `includes/lifecycle_restore.php` και `includes/maintenance_controller.php` στις αντίστοιχες θέσεις. Μην αλλάξετε config, κλειδιά ή ιδιωτικούς φακέλους. Η αντιγραφή αυτών των αρχείων δεν εκτελεί SQL και δεν εγκαθιστά από μόνη της την 1.1.0.
3. Ορίστε μία φορά ξεχωριστό λογαριασμό συντήρησης στη βάση της συγκεκριμένης εφαρμογής, μέσω των ιδιωτικών `APP_MAINTENANCE_DB_USER` / `APP_MAINTENANCE_DB_PASS`. Για δημιουργία/μεταβολή πινάκων και δεδομένων χρειάζονται SELECT, INSERT, UPDATE, CREATE, ALTER, REFERENCES. Δεν απαιτούνται γενικά δικαιώματα σε άλλες βάσεις ή αλλαγή του runtime λογαριασμού. Για συγκεκριμένες μεταβολές DELETE ή για επαναφορά με DROP απαιτείται πρόσθετη, ρητή εξουσιοδότηση του υπευθύνου βάσης· δεν χορηγούνται αυτόματα.
4. Οι επόμενες ενημερώσεις γίνονται από τη συνηθισμένη οθόνη, με το υπογεγραμμένο ZIP που αντιστοιχεί ακριβώς στην τρέχουσα έκδοση.

Η προετοιμασία είναι μία φορά για αυτή τη δυνατότητα. Μελλοντικές αλλαγές στον ίδιο τον προστατευμένο μηχανισμό, ειδικές SQL λειτουργίες εκτός της υποστηριζόμενης λίστας ή πρόσθετα δικαιώματα hosting μπορεί να χρειάζονται χωριστή παρέμβαση. Οι μεταβολές βάσης δεν αποκτούν αυτόματα επιπλέον δικαιώματα.

## Δηλώσεις νέων πινάκων από τον εκδότη

Το υπογεγραμμένο manifest μπορεί να περιέχει το προαιρετικό `new_tables`, με τα λογικά ονόματα νέων πινάκων **χωρίς DB_PREFIX**:

```json
{
  "from_version": "1.1.0",
  "version": "1.1.1",
  "min_php": "8.2.0",
  "description": "Προσθήκη σημειώσεων νέας λειτουργίας",
  "files": [],
  "migrations": ["01_create_feature_notes.sql"],
  "new_tables": ["feature_notes"],
  "delete": []
}
```

Το αντίστοιχο SQL αρχείο, μία εντολή ανά αρχείο, χρησιμοποιεί το πρόθεμα:

```sql
CREATE TABLE `{{prefix}}feature_notes` (
    id INT AUTO_INCREMENT PRIMARY KEY,
    note VARCHAR(255) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Ο `bin/sign_update.php` υπογράφει και τη δήλωση `new_tables`. Επιτρέπονται έως 512 πρόσθετοι πίνακες, πεζά λατινικά/αριθμοί/underscore, αρχικό γράμμα και έως 64 χαρακτήρες μαζί με το πραγματικό DB_PREFIX. Απορρίπτονται διπλότυπα και ονόματα με διαδρομές ή διαφορετικό schema. Κάθε δηλωμένος νέος πίνακας πρέπει να έχει αντίστοιχο CREATE TABLE μέσα στο ίδιο υπογεγραμμένο πακέτο. Το πακέτο πρέπει να ενημερώνει και τον επιχειρησιακό κώδικα που χρησιμοποιεί τον πίνακα, συμπεριλαμβανομένης της υποστήριξης προθέματος όπου χρειάζεται.

Η επαλήθευση δεν μεταβάλλει τη βάση ή το ιδιωτικό μητρώο. Αν ένας μη αναγνωρισμένος πίνακας υπάρχει ήδη με το ίδιο όνομα, η ενημέρωση απορρίπτεται: δεν γίνεται αυτόματη ανάληψη ιδιοκτησίας ξένων πινάκων.

Μόνο μετά την επιβεβαίωση και το επαληθευμένο backup καταγράφονται οι δηλώσεις στο ιδιωτικό `schema-ownership.json`, πριν ξεκινήσουν τα DDL. Από εκεί και πέρα οι πίνακες συμμετέχουν σε inventory, backup, έλεγχο επαναφοράς και σειρά απεγκατάστασης, ακόμη και σε επόμενο αίτημα. Ένα μελλοντικό ALTER στον καταγεγραμμένο πίνακα δεν απαιτεί νέα χειροκίνητη αλλαγή της μηχανής.

Τα παλαιά υπογεγραμμένα πακέτα χωρίς `new_tables` εξακολουθούν να λειτουργούν. Το μητρώο μένει στον ιδιωτικό φάκελο της ίδιας εγκατάστασης και δεν αντιγράφεται σε άλλο σχολείο. Πρέπει να διατηρείται μαζί με τις υπόλοιπες ιδιωτικές καταγραφές συντήρησης για ανάκτηση.

## Σε αποτυχία

Τα MySQL DDL δεν είναι συναλλακτικά αναστρέψιμα. Αν ξεκινήσουν και αποτύχει η ενημέρωση, παραμένει ενεργή η συντήρηση με αναφορά στο backup. Το μητρώο διατηρεί τα δηλωμένα ονόματα ώστε τυχόν μερικώς δημιουργημένοι πίνακες να αναγνωρίζονται στην ανάκτηση. Δεν ανοίγει η εφαρμογή αυτόματα πάνω σε μερικώς ενημερωμένη βάση. Ο υπεύθυνος ακολουθεί το [MAINTENANCE.md](MAINTENANCE.md) και τις απαιτήσεις επαναφοράς.

## Δοκιμές

Το `tests/test_lifecycle_tables.php --mysql --host=localhost --port=3306 --user=DATABASE_ADMIN` δημιουργεί τυχαία, ξεχωριστή δοκιμαστική βάση και την αφαιρεί στο τέλος. Κωδικός δοκιμών δίνεται μόνο μέσω `TEST_MYSQL_PASSWORD`. Δεν φορτώνει config σχολείου και δεν χρησιμοποιεί πραγματικά στοιχεία ή κλειδιά εκδότη. Ελέγχει ολόκληρη τη ροή CREATE/seed, επόμενου ALTER, backup/restore και ανάκτησης μετά από αποτυχία, με και χωρίς DB_PREFIX, καθώς και τις περιπτώσεις απόρριψης.
